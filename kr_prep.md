# Подготовка к КР №4

## 1. Когда я выберу rebase, а когда merge? Почему?
Rebase — для своей локальной feature-ветки, которую ещё никто не забрал:
перед PR делаю `git rebase main`, чтобы ветка шла поверх свежего main
и история была линейной (плюс `rebase -i`, чтобы убрать WIP-коммиты).
Merge — для интеграции в общие ветки (main, release) и для веток, с
которыми уже работают другие: merge не переписывает историю и явно
показывает, когда и что было влито.
Пример: сам пилю feature/login три дня — rebase на main; влить готовую
фичу в main — merge (или squash merge через PR).

## 2. Что будет, если сделать rebase публичной ветки, с которой работают коллеги?
Rebase создаёт новые коммиты с новыми хешами, а старые «исчезают».
Чтобы запушить, придётся делать `push --force` — и у коллег история
разойдётся с удалённой: их `git pull` попытается слить старые и новые
версии тех же коммитов, появятся дубли и конфликты, а чужие коммиты,
запушенные после моего fetch, force push просто затрёт.

## 3. Зачем нужен multi-remote и где он применяется?
- Зеркало/бэкап: основной репозиторий на GitHub, копия на GitLab
  (или на своём сервере) — если один сервис недоступен или заблокирован,
  код не потерян.
- Open Source: `origin` — свой форк, `upstream` — оригинальный репозиторий,
  из которого подтягиваются обновления.
- Разные CI/CD: например, код живёт на GitHub, а пайплайны или деплой
  запускаются из GitLab.
- Миграция между платформами без остановки работы команды.
